# KipSeek 内容保持机制与 MorphForge 存储路线

日期：2026-10-18。只读核查用户私有项目 KipSeekTextSync；GitHub master 与现有只读检出均为 `8f2e5464b5bd31eea942c42ccdafb5758d8c3d02`。没有修改该仓库或 Unity 工程，也没有运行客户端。早先的 [KipSeek 核查](../../../vrc-ai-world/docs/07-kipseek-reuse.md) 仍适用。

## 结论

已有项目具备可复用的分页内容保持设计。MorphForge 的下一步应验证同一机制在几何数据上的移植，并比较路由结构的成本，而非重新寻找一个完全未知的保持机制。

优先候选是材质属性保存内容、按输入通道分层并用页号选择写入状态。GPU 反馈纹理是更高容量的研究方向，Unity 的相关功能存在，但 Avatar 中的数据桥接、实例隔离和远端行为尚未验证。

## 内容保存在哪里

源码定位：

- `Scripts/KipSeek_AnimatorBuilder.cs:414`：动画绑定 `MeshRenderer.material.*`。
- 同文件 `:432`：为每个板、每个字符属性生成路由层。
- 同文件 `:444`：Simple1D BlendTree 通过两个锚点动画把输入值映射成材质属性值。
- 同文件 `:457–485`：Board 与 Ptr 匹配时进入 Active；地址不匹配时回到 Standby。两个状态都关闭 Write Defaults；Standby 使用不修改字符属性的占位动画。
- `Shaders/KipSeek_CJKTextShader.shader:476`：按槽读取 `_CharRowN` / `_CharColN`。

每个字符有两个预先定义的材质数值。共享入参改变时，只有地址匹配的路由写入对应属性；其他页的属性沿用此前结果。因此保留的是运行中的动画/材质状态。Shader 每帧重新读取这些值绘字，并不是在板子图像上不断叠画，也没有使用纹理反馈保存文本。

例：先将共享入参写入页0，切到页1后相同入参开始驱动页1对应属性；页0对应路由停止写入，其结果继续用于显示。Avatar 重建、材质重建或未接收过此前页的客户端需要重新填充状态。

## 核查到的容量

| 项目 | 当前多板版本 |
| --- | ---: |
| 板数 | 3 |
| 每板字符数 | 80 |
| 每字符材质数值 | 2 |
| 材质数据数值合计 | 480 |
| 一次共享数据数值 | 8 |
| 同步参数 | 1 Bool、2 Int、8 Float |
| 同步状态预算 | 81 bit |
| 已提交 Controller 层数 | 481 |
| 已提交 Controller 状态数 | 962，均 WD Off |

这些是代码与资产的静态事实，不是新的客户端性能实测。保留数据的容量与同步入参预算不同：81 bit 是当前共享总线的状态预算，480 是预留存储数值数量。

按每个稀疏体素保存 XYZ 和样式4个数值，同样480个数据属性相当于120个体素槽。256个体素需1,024个数据属性；沿用逐属性一层的结构就需约1,024个数据路由层。材质属性并不因此被证明只能有480个，实际扩展瓶颈需要测量。

## 路由优化候选：按输入通道分层

保留已经理解的 Simple1D + WD Off + 占位状态。把“一个保存属性一个层”改为“一个输入通道一个层，每页一个写入状态”。

以16个共享数据通道、每页4个体素为例：

- 256个体素共有64页，保存1,024个数值。
- 16个数据路由层，每层按页号进入64个对应的写入状态，另有待机状态。
- 每个写入状态仍是独立的 Simple1D BlendTree，只写对应页的一个材质属性。
- 输入通道0在页0写槽0的X，在页1写槽4的X；其他通道以相同方式路由。

目标是减少同时维护的大量层。属性、动画绑定与状态数量仍随容量增长，不能按层数比值宣称 CPU 提速倍数。跨状态保持、退出时值是否变化、和其他 FX/构建优化的相互影响均需与原结构对照验证。这是设计候选，尚未实现。

不直接用大型 Direct Blend Tree 合并所有 WD Off 路由。VRCFury 维护者的技术文档明确记录 Direct Blend Tree 与 WD Off 组合可能出现值倍增、逐帧漂移等问题；这与当前依赖 WD Off 的保持机制有冲突，不能当作安全的机械替换。

## 更高容量候选：GPU 反馈存储

概念数据流为少量 Animator 输入 → GPU 写入 pass → 双缓冲纹理 → 几何 Shader。命中地址时覆盖目标像素，否则保留上次像素值。这样长期数据放在纹理中，Animator 不再为每个保存数值配置路由。

一个64×64 RGBA8纹理有4,096个四通道记录位；若每像素保存XYZ格索引和样式，原始单缓冲为16 KiB、双缓冲为32 KiB。该算术只描述存储资源，不承诺4,096个体素可在客户端低成本存储并绘制，更不提高 OSC 传输速率。

Unity 2022.3 的 Custom Render Texture 支持 Realtime 更新和双缓冲读取上一帧；它给出了研究基础。仍需逐项验证：

1. Animator 实际动画化的材质实例，能否把参数送到真正执行写入的材质。Renderer 上的实例不应假定等于 CRT 引用的材质。
2. Avatar 中的更新是否确实由允许的机制触发，且不会因不可见或更新顺序丢写。
3. 同一 Avatar 的多个实例、不同玩家是否各有独立缓存，避免共享纹理互相覆盖。
4. 重载、重新显示与晚加入后的全量恢复。

若改用 Camera 驱动 RT 写入，必须考虑官方远端相机限制：远端相机加载时禁用；非好友且未手动 Show Avatar 时可能被移除。CRT 在 Unity 中可自动更新这一事实，不等于该完整链路已在 VRChat Avatar 中成立。

## 发送与恢复也需补齐

`osc/kipseek_stream.py:144` 先发 Board、Ptr，再逐个发载荷，没有能从源码证明的原子提交。`:157` 在队列非空时发一页；空闲时不做周期全量刷新。

对于几何建议把每页定义为绝对值覆盖，外部维护权威场景与槽位映射；脏页优先、空闲持续轮播完整快照，包含删除后的空槽。重复收到同一页应得到相同结果。写入门控与数据稳定等待需要测试；增加 Commit、序号或 OSC bundle 本身不保证跨玩家原子性。

外部队列按地址合并最新脏页，可避免反复发送过期施工状态。若用户希望逐步观看每个施工阶段，应另外保留施工步骤队列，不能与“只追最新状态”的传输队列混用。

## 建议验证顺序

先做少量体素的原路由基线，写两页后停止发送并持续观察，再覆盖其中一页、删除一个体素，检查其他页保持。随后在相同内容下比较按通道分层的接收器，并测256槽位的 CPU/GPU 开销。GPU 存储另做极小的随机写入、停发保留、双实例隔离实验，通过后再扩大。

无论选哪种存储，区域盒体和后端表面合并都可以独立减少需要传输及保存的记录数量。一面墙优先编译为一个盒体，或少量合并表面，不必让显示器逐块保存。
