# 长方体粒子：把连续体素编译成盒体

日期：2026-10-18。状态：设计与几何核算，尚未实现尺寸接收、精确发射、UV平铺或盒体删除，不报告Avatar验证通过。

## 结论

可以优先验证SetBox：传起点、长宽高及共享外观/运动数据，在Avatar内发射一颗长方体Mesh粒子。Unity2022.3的Mesh粒子与3D Start Size提供原生基础，每颗粒子能保留出生尺寸。尺寸不必另外塞进RGBA。

外部Draft/Published继续保留可编辑体素；发送编译器把相邻、完全相同描述的格子合并为不重叠轴对齐长方体。VRChat显示压缩后的盒体，后端负责局部编辑后的拆分和重合并。单位体素是size=[1,1,1]的特殊盒体。

## 两种不同的批量语义

| API | Avatar结果 | 收益/代价 |
| --- | --- | --- |
| SetBox(min,size,...) | 一颗拉伸Cube粒子 | 一条记录描述很多格，减少粒子和面数；局部编辑需拆分 |
| FillBox(min,size,...) | 接收端自行展开成很多单位粒子 | 可省网络命令，但仍消耗逐格容量、发射时间；本地循环解释器尚未验证 |

如果FillBox只在外部展开后逐个发OSC，不能按一条命令计算传输收益。当前建议先试SetBox，接收逻辑更贴近原生出生属性。

## 示例与成本

```python
SetBox(
    min=[128,128,128],
    size=[20,10,1],
    styleId=1, tintId=0, motionGroup=0, phase=0,
)
```

格长0.25m时对应5m×2.5m×0.25m的墙体。若没有不同样式、孔洞或运动差异，可以用一颗Cube粒子表示。

| 表示 | 粒子数 | 朴素几何三角形数 | 沿既有两块/批基线的命令数 |
| --- | ---: | ---: | ---: |
| 200个独立单位Cube | 200 | 2400 | 100 |
| 一个合并盒体 | 1 | 12 | 1 |

前者按0.4s/命令为40s；后者仅网络时隙规划为0.4s，单状态候选为0.2s。后者不包括真实到达/发射/校验/刷新，不是实测可见时延。不能把200倍几何缩减写成所有场景固定200倍吞吐。

## 建议10字段记录

| 槽 | 内容 | 范围 |
| --- | --- | --- |
| D00–02 | minXYZ | 各0–255 |
| D03–05 | sizeXYZ减1 | 各0–255，表示1–256格 |
| D06–07 | styleLo/Hi | 各0–63 |
| D08 | tintId | 0–63 |
| D09 | motionPhase | 3bit运动组+3bit相位 |
| D10–15 | 预留 | 首版0 |

min+size必须逐轴≤256。单条SetBox占10个Int槽，当前16槽足够，无需新增常驻同步参数。操作码通过Extended或后续规划分配，不冒用现有SetVoxels布局。

两个相同描述的盒体也可研究共享4个描述槽、各6个位置尺寸槽，正好16槽；数量可放描述字段未用高位。这不是首轮必须能力。

## 出生位置与持久尺寸

默认h=0.25m、中心锚点，原生中心：`anchor + (min + size/2 - 128)*h`。native startSize3D为`size*h`，速度与旋转为0，粒子Custom simulation space保持固定场景根。

中心可能在半格或格边，不再总是单体素中心。删除/更新接口不能盲目沿用旧整数格中心公式。

接收器可以研究两层定位节点：父节点由min驱动，子节点由size/2驱动，使Unity变换相加得到出生中心；尺寸输入同时驱动3D Start Size。避免假设Avatar能执行C#算术，动画绑定和尺寸保留需通过Unity API创建及验证。

禁止只修改发射器/父节点整体缩放来默认获得独立盒体尺寸；应验证已经出生的旧盒体不受下一次尺寸输入影响。

## 材质平铺

直接拉伸Cube的0–1 UV会把一张方块贴图拉长。显示Shader需要按盒体各面的格数重复采样，并保留六面不同贴图/UV方向及染色规则。

UV按逻辑格/盒体静止坐标计算，再应用运动，避免运动时贴图在表面滑动。图集边缘、mipmap与法线/光照应另测。纹理数组/图集仍随Avatar预上传，本提案不新增运行时下载资源能力。

## 合并条件

仅合并共享完整描述的相邻格：样式、染色、静态方向变体、运动组、个体相位、渲染类型及形状解释必须一致。带不同生长/施工时间的粒子若需要独立效果，也不能无条件合并。

后端使用确定性贪心盒体覆盖等算法，不承诺全局最少盒数。复杂零散多色形状可能退化到一格一盒；大平面和实心规则建筑收益较大。此处为三维盒体合并，不与二维外表面greedy meshing混为同一算法。

## 删除一格时的拆分

原生Trigger Kill删除的是整颗粒子。它不能在大盒体内局部挖洞，碰撞检测边界也不等于盒体Mesh表面。

外部先修改体素目标，再针对被影响盒体求差：一个轴对齐盒体减去一个内部单位格，可拆成最多6个不重叠盒体；薄墙中间挖一格可拆成最多4个矩形盒体。若改色，则保留碎片后另加一个新颜色单位盒体。

20×10×1墙挖掉格[10,5,0]，按半开区间切分可得到：

```text
[0,10) × [0,10) × [0,1)
[11,20) × [0,10) × [0,1)
[10,11) × [0,5) × [0,1)
[10,11) × [6,10) × [0,1)
```

剩余199格，共4个盒体。后端删除旧整盒、再发4个新盒；在容量和区域后台版本能力允许时可隐藏准备后切换，否则可能看到短暂重建。

多次挖洞会增加碎片，应对脏空间单元重新合并，并在发布前检查编译后的盒体粒子数量。不能因为一面墙压缩成一盒就宣称任意百万格场景都能低成本显示。

## 盒体删除定位仍是关键门槛

后端可使用稳定boxId追踪编译结果和已发快照，但尚未获得Avatar按任意ID检索粒子的能力。不要把SetBox(id)的后端标识当作运行时随机访问已解决。

候选删除方式：发送旧盒体min/size重新定位其中心，用中心附近的小Trigger杀掉整盒；或重建受影响显示单元。长方体的原生尺寸会影响粒子触发边界，小擦除体仍可能碰到相邻大粒子的边界，所以需独立调小Radius Scale并验证；若无法可靠区分就先采用分区重建。

逻辑EraseBox在盒体模式下需要由后端求所有相交旧盒体并拆分；只用该空间里的Trigger不会自动得到体素级布尔差，特别是相交盒体中心在擦除区域之外时。

## 与现有仿真/发布设计的结合

```text
Draft体素 → Published体素目标 → 盒体编译缓存
    → 与已发盒体快照计算差异 → 单写入发送器 → Mesh粒子
```

仍只有两套可编辑体素空间；盒体是P的编译产物。发送台账改为记录实际发过的盒体描述，不继续按旧单位体素差量假定Avatar存了每一格。

刷新与队列ETA按实际盒体命令数、拆分/删除数和协议时隙计算。模型仍按体素建模、挖洞、换色，无需手动猜合并结果。完整尺寸、样式与运动成为快照的组成部分。

## 首轮验证

1. 一个Cube Mesh粒子分别发1×1×1、20×10×1、非均匀三维盒体；旧尺寸在新命令后保持。
2. 原生出生中心、半格边界、非均匀尺寸与Custom simulation space正确。
3. 按格重复纹理、六面映射、运动组的整体变换。
4. 大小盒相邻时删除指定旧盒，检查误删与Ring Buffer。
5. 挖墙洞、内部挖格、改色：后端差分覆盖无重叠/遗漏，真实替换不超容量。
6. 单状态/两阶段下实际可见延迟和编译后刷新速度。
