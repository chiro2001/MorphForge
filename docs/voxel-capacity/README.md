# 固定单位体素的空间与传输收益

日期：2026-10-18。用户提出只传单位立方体及颜色/材质。本文分析其收益和边界，不创建体素原型；估算沿用 [通道分析](../channel-capacity/README.md) 的有效 16 数值/批、0.2 秒/批假设。计算见 [estimates.json](estimates.json)。

## 结论

对于方块式场景，固定体素可以显著提高同一同步预算下的表达效率。收益来自立方体形状与尺寸已知、坐标离散、外观表复用。它减少每块需要的新信息，但不会自动提供可变大小的接收内存或无限几何容量。

建议区分四个量：可寻址网格范围、同时保存的非空体素数、每秒可修改体素数，以及实际绘制的面数。

后续已核查用户文本项目的具体保持机制，并比较 [按通道分层路由与 GPU 存储方案](text-storage-review.md)。已有文本保持机制可以复用；几何移植与路由优化尚待验证。

进一步的 [替代架构调研](alternative-architectures.md) 对比相机反馈、CRT、Parameter Driver寄存器、粒子记录、参数化场景和GPU命令解释器，重点分析如何减少逐槽位Animator的CPU成本。

粒子路线另有 [增删设计](particle-editing.md) 与 [方块样式编码、资源包导入](block-styles-and-resource-packs.md)，均为待验证设计。

最新的 [运动与传输协议v1草案](motion-protocol-v1.md) 规划共享OSC入口、24bit粒子编码、共享运动组和VRChat网络时钟，并明确RGBA字段重新分配的取舍；[JSON摘要](motion-protocol-v1.json)可供后续实现参考，尚未落地验证。

## 一个体素只需四个数值

建议最简单记录为 `x, y, z, style_id`。格子边长 h 和模型原点全局约定，坐标是整数格索引，0 号样式可表示空，其余 ID 对应预置颜色/材质组合。

在 64³ 网格和 64 个样式状态的例子中，XYZ 与样式各只有 64 个候选值。每项可映射到一个同步 Float，再四舍五入还原整数；不需要把毫米级坐标作为单独数值传输。理想稳定接收时，格索引可以无歧义恢复，造型精度由体素边长决定。

官方说明同步 Float 占 8 bit，但有 255 个取值，并非任意 0–255 字节均可直接无损映射。上述 64 级用法保留了量化间距。若以后紧密打包数据，应单独验证 Float 编码或使用 Int 路线。

按每个同步标量消耗 8 bit、位置采用单标量精度、外观用一个 ID 的比较：

| 表示一个立方体 | 数值字段数量 |
| --- | ---: |
| 12 个独立三角形的 XYZ + 外观 ID | 109 |
| 已知立方体索引、8 个共享顶点 XYZ + 外观 ID | 25 |
| 轴对齐参数化盒体：中心、尺寸、外观 ID | 7 |
| 固定体素：XYZ 格索引、外观 ID | 4 |

因此相比当前逐面传顶点约省 27 倍，相比共享顶点约省 6 倍；相比本来就紧凑的参数化盒体约省 1.75 倍。以上是字段数比值，没有加入寻址/版本等公共开销，也不意味着体素优于所有网格压缩形式。

## 空间范围与更新速度

| 每轴格子数 | 逻辑格子数 | 边长 0.1 米时的每轴范围 | 边长 0.25 米时的每轴范围 |
| --- | ---: | ---: | ---: |
| 32 | 32,768 | 3.2 米 | 8 米 |
| 64 | 262,144 | 6.4 米 | 16 米 |
| 128 | 2,097,152 | 12.8 米 | 32 米 |

表中是可寻址范围，不是可以全部存储并显示的承诺。扩大 h 会增大范围、降低造型分辨率；分块坐标可以扩大寻址范围，但仍要计算存储、同步和绘制成本。

最简单的四字段记录，16 个有效字段一批可容纳四块；若每 0.2 秒稳定收到一批，理想为 20 块/秒。

| 累积非空体素 | 连续写入理想时间 | 每块 12 三角形时的原始面数 |
| --- | ---: | ---: |
| 256 | 12.8 秒 | 3,072 |
| 1,024 | 51.2 秒 | 12,288 |
| 4,096 | 204.8 秒 | 49,152 |

前提是有效字段容量已扣除公共协议状态，槽位可连续写入，且不需等待或重复。随机改一块却需要重发所在页其他数据、帧间提交、重传和晚加入刷新，都会改变净速度。这仍是规划假设，不是已测得的多人性能。

如果传输固定区域的完整快照，可约定扫描顺序，由页号和页内位置推导 XYZ，每格只发一个样式字段。在同一理想通道假设下，可以达到 80 格/秒；8³ 区块的 512 格需 6.4 秒，64³ 整体需约 54.6 分钟。这里空格也占传输量，因此适合稠密区块，不适合零散物体；它也不解决接收端缓存容量。页号和区域原点仍需协议字段，不能省略整套寻址信息。

## 颜色与材质

优先用共享样式表：比如 `style_id=5` 表示某种木头颜色和纹理组合。体素自身不再分别携带 RGB、粗糙度、金属度等字段；修改表项也可同时影响所有引用体素。

这些 ID 选择的是已上传的 Shader/外观能力。新颜色可研究表项更新；新贴图、Shader 或 Material 资产不能因收到一个 ID 就自动出现在 Avatar 中。多种表面类型需要在显示器里预先实现相应采样或着色逻辑。

## 区域操作会带来更大收益

除了 `SetVoxel`，可研究 FillBox、EraseBox、PaintBox、Repeat 等。例：20×10×1 的同色墙含 200 块，逐块在理想模型中需 10 秒；一个起止坐标和样式的区域命令可以在很少的字段中描述它。

但命令只有在接收端能本地展开、存储或直接绘制该区域时才节省传输。如果后端仍展开为 200 条单块记录发送，就仍承担逐块开销。

Avatar 没有可随意运行自定义脚本的场景编辑器。区域解释器需依赖预上传的 Animator/Shader 或其他已验证机制，不能把 `FillBox` 的名字当成已实现的批量写入能力。

## 绘制方式与体素数据模型可以不同

每块无条件保留六个面是最简单的参考实现。后续可隐藏内部面，或由外部后端把相邻同材质面合并为矩形，再把矩形参数传给 Avatar。

一个同材质的完整实心长方体，外表面可以用六个矩形表示。Greedy meshing 可合并这样的相邻面，但零散、颜色多变的形状不一定能获得同样压缩收益。算法依据见作者原文 [Meshing in a Minecraft Game](https://0fps.net/2012/06/30/meshing-in-a-minecraft-game/)。

建议长期考虑：后端保存可编辑体素，输出层按情况传单块、区域描述或合并后的表面片。这样 AI 可以继续按体素操作，不必让 Avatar 始终保存完整稠密网格。

## 不能忽略的容量限制

64³ 网格若每格仅记一字节样式，逻辑数据已有 256 KiB；若每格都绘制完整立方体，则有 3,145,728 个三角形。可寻址体积很大，不意味着 Avatar 可以低成本建满它。

当前原型每个驱动数值有独立 Animator 层，不能将这一结构原样扩成大体素存储。可以先用稀疏体素槽位池，只为有限数量非空体素保留 XYZ 和样式，再测存储、驱动及绘制开销。

这里的“槽位”是预留的显示/存储位置，不等于网格坐标。外部后端可维护 XYZ 到槽位的映射，并通过公共页地址改写对应槽位，避免假定 Avatar 内已经具备稀疏字典查找能力。只有确认各远端能保留已写入的页，才可能复用少量同步参数逐页累积出更多方块；后来加入者仍需要快照或持续轮播恢复。

初步候选是 64³ 逻辑网格、0.25 米格长、64 个样式状态、先 256 个非空槽位，再尝试 1,024 个。它表达 16 米见方范围内的稀疏结构，并不承诺同时填满 262,144 格。

现有 8 三角形载体需要更换为体素或表面片载体；当前没有体素解码与绘制实现。它仍是 Avatar 的视觉几何，不会自动得到可站立碰撞。
