# 控制通路与API核查：先压缩控制头

日期：2026-10-18。当前任务仅分析MF_Ctl等控制字段及API；不调整MF_D数量，不实现共享通道分页，不修改Unity资产。以下是未实现的接口草案，不等同于客户端已支持。

## 旧32bit头的职责

| 字段 | 旧分配 | 原职责 | 本次判断 |
| --- | ---: | --- | --- |
| MF_Ctl | 8bit | 版本2、操作码4、阶段2 | 版本可配置期绑定；操作码和阶段保留 |
| MF_Seq | 8bit | 区分命令与识别重复 | 保留但可缩短，不能当回执或可靠序列号 |
| MF_Target | 8bit | 运动组/空间分区目标 | 属于具体API参数；体素已有XYZ地址，不必每条都带通用Target |
| MF_Epoch | 8bit | 区分清空/重建前后的场景代数 | 普通简化头可省，稳健/分片模式另议 |

旧头是容量规划时为扩展留出的上限，不是完成过必要性证明的最低控制成本。尤其Target的256个值远超首版7个可写运动组的需求。

## API列表与编码候选

| opcode | API | 数据参数 | 语义/状态 |
| ---: | --- | --- | --- |
| 0 | Nop | 无 | 不执行场景修改；可用于退出未提交准备，具体接收状态机待验证 |
| 1 | SetVoxels | 1–2条完整体素记录 | style=0删除；非零覆盖；沿用修订B的16槽批布局 |
| 2 | EraseBox | minXYZ、maxXYZ | 按逻辑格的闭区间删除，原生擦除机制待验证 |
| 3 | SetMotionGroup | groupId及16字段运动配置 | 绝对覆盖组配置；0组为静态且不可写 |
| 4 | SetDisplay | visible、packId | 全局显示/预上传外观包选择；首版功能子集待定 |
| 5 | ClearScene | 无或可选清空选项 | 清空粒子及重置运动组；清空实现待验证，不清除传输去重状态 |
| 6 | Reserved | — | 暂不执行，不为未确定功能单独预占字段 |
| 7 | Extended | subOpcode及其参数 | 为时间线、特殊形状等保留入口；未实现 |

所有API为设计契约。具体数据读写、锁存和执行效果仍需原型验证。并非每个API都要有独立OSC地址；它们共用MF_Ctl和数据通道。

SetVoxels、EraseBox和ClearScene描述绝对目标结果，适合重放修复；但迟到的旧ClearScene会删除新内容，因此“操作本身幂等”不能取代顺序与恢复设计。

## 不必增加opcode的上层接口

| 对外接口 | 编译为 |
| --- | --- |
| SetVoxel | 单条SetVoxels |
| DeleteVoxel | style=0的SetVoxels |
| PaintVoxel | 后端读出该格其他字段，发新的完整SetVoxels |
| MoveVoxel | 删除原格，再设置新格；不承诺两步原子 |
| PauseGroup / ResumeGroup | 修改playback/frozenPhase等后覆盖SetMotionGroup |
| Undo / Redo | 后端历史生成差异，再调用基础API |
| ReplaySnapshot | 调度ClearScene、组配置、体素记录等，不自动表示显示原子切换 |

版本、格长、通道数、样式表约定优先写入Avatar构建清单并与发送端配对。协议不匹配时发送端应拒绝发送，不把这称为已实现的自动协商。

BeginSnapshot/EndSnapshot、场景代数和时间线参数可作为将来的扩展API或数据内容。仅在存在相应双缓冲/恢复机制时才增加有实质语义的快照提交命令；不为了名字本身预留永久独立同步参数。

## 推荐基础控制头：一个8bit Int

```text
MF_Ctl bit 0…2：opcode，0…7
MF_Ctl bit 3：phase，0准备、1执行
MF_Ctl bit 4…7：seq，0…15，循环使用

MF_Ctl = opcode | (phase << 3) | (seq << 4)
```

phase=0表示准备阶段，不能据此修改场景；phase=1请求按已稳定且锁存的数据执行。反复看到相同控制字不应反复发射。seq在下一条逻辑命令才变化，不因同一命令重发而变化。

这不代表两个阶段必须各占一个完整网络周期。后续 [吞吐复核](../simulation-publish/throughput-audit.md) 将其视为保守对照，并要求比较单状态输入、本地锁存/执行与同描述批次；快速方案需新接收器验证，不能仅删除等待。

MF_Ctl=0为初始不执行状态。取消尚未提交的操作可设计为Nop/回准备状态；取消已经执行的修改需要后端发送反向差异，不能把低位phase当作撤销功能。

## 单条命令准备与区域显示提交是两层语义

MF_Ctl的phase指单条命令：先让坐标、外观等输入稳定并进入工作快照，再执行这一条场景操作。它不表示已缓存一整栋建筑，也不自动让许多粒子变化在同一帧出现。单条粒子操作本身还可能经过擦除、撤离擦除体和发射等本地阶段。

用户提出的两种显示效果可另设为编辑会话的presentation属性：

| 显示方式 | 数据应用与可见效果 | 资源需求 |
| --- | --- | --- |
| progressive | 每条完整命令执行后更新可见部分，看着模型逐步施工 | 一个可见版本即可 |
| staged | 保留旧部分可见，在隐藏版本中逐步构建新部分，完整后切换 | 被编辑范围的新旧两份显示存储 |

只隐藏当前区域、原地重建后再显示，会留下暂时空缺；它可作为较省资源的批量显示方式，但不是旧版本一直保留到替换完成的staged效果。

可评审的上层API为BeginEdit(regionId,presentation)、基础写入/擦除API、CommitEdit、CancelEdit。mode在BeginEdit参数中选择，区域和编辑上下文只在必要时建立，不为每块新增永久同步开关。可先使用Extended操作入口，具体子操作号、编辑ID与分片恢复布局尚未确定。

staged需要原生擦除和发射只操作隐藏版本，隐藏版本仍能更新；如果同时更新共享运动参数、样式映射，也要隔离相应版本。接收器需要能判定待显示内容已完整，不能只收到Commit就假定所有内容齐全。各客户端可分别在自身就绪后切换，不承诺全玩家同帧提交。

CancelEdit对未显示的隐藏版本可以丢弃；progressive已经执行的修改需要后端保存旧状态并发送恢复差异，不能假定自动回滚。粒子系统的双版本隔离、容量开销和切换效果均未实现验证。

如果opcode只用3bit但仍单独注册为Int，它依然消耗8bit同步预算；这里的节省来自把多个子字段合成同一个Int，不是声明一个“3bit Int”。8个Bool理论上也占8bit，但控制位会跨多个参数到达，不能直接假定同样的控制字一致性。

## 目标参数的放置

SetVoxels通过XYZ定位；EraseBox通过坐标范围定位；SetDisplay的packId在该命令数据中。因此三者无需通用MF_Target。

SetMotionGroup的目标为3bit。当前16字段运动配置最后的flags只用bit0反向、bit1逐块支点，其余尚未使用；可采用：

```text
运动命令 D15 bit 0…1：原运动标志
运动命令 D15 bit 2…4：groupId，0…7（0不可写）
运动命令 D15 bit 5…7：预留0
```

这样仍是16字段完整运动配置，不增加数据通道数量；该API内部沿用低2bit标志，高位只用于接收路由。其他API对D15可有不同定义。未来超过8组、更多标志或空间分区时需要扩展布局，不能沿用旧的“独立8bit Target”解释。

## 成本与取舍

原控制32bit → 基础候选8bit，节省24bit。仅做同口径比较，保持此前89bit原Avatar和16个Int载荷不变：89+128+8=225bit，余31bit。此数字不是重新确认当前面捕Avatar余量的实测值。

没有Seq、只保留3bit opcode和1bit phase的4bit方案可用4个Bool表达，但失去命令标识且控制位可能错位到达，不作为首选。单独一个Int无论只用4bit还是8bit均收8bit预算。

8bit方案与旧32bit方案并非完全等价：

- 序号只有16种，缩短重复识别窗口，不能判定任意延迟旧命令的新旧关系。
- 普通数据不携带Epoch，不能逐条拒绝属于旧场景代数的命令；若目标需要这种能力，应在增强头保留代数，或另设完整恢复协议。
- 省略每帧版本要求发送端与构建清单严格配对。
- phase只是写入意图，没有让数据字段与控制字段变成原子消息。
- seq不是所有观看者的ACK；本机OSC回读也不代表远端收到。
- Int里打包位域需要接收路由解码，不能假定能在Avatar执行C#位运算。可研究固定状态/动画映射，但CPU成本和边界需实测。

官方说明自定义参数通常采用Playable同步，更新约0.1–1秒，且不适合快速同步；因此不能把任一控制头大小当作0.2秒逐包可靠交付的证明。Parameter Driver也在状态进入时执行，阶段设计必须实际触发接收状态而非只改变载荷。

## 与下一轮共享通道配置的边界

这个8bit头针对一条完整命令可装入当前载荷的基础模式。以后减少MF_D数量并拆成多页，还要决定片号、组装长度、收齐标志、超时和提交方式；8bit头已经用满，不能未经设计就宣称所有小通道配置都只需这8bit控制。

下一轮应基于这里的API集合，分别估算完整命令模式与分片模式的真正必要控制信息，再选择通道数量。此轮不修改MF_D布局和配置。
