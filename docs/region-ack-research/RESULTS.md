# OSC回读、本机ACK与连续区域编码

2026-10-21。研究与只读测试，不是已发布协议能力。桌面0.15.1只修复暂停恢复；没有修改Unity资源、向9000发送新命令、替换头像或接管用户的发送通道。

## 已完成的真实回读

从gamepc上实际VRChat进程的TCP监听发现OSCQuery端点，HOST_INFO报告支持VALUE查询。真实头像树暴露687个MF相关参数，包括输入、解码快照、本地worker序号、Busy、Ready和DoneCount；没有为这次读取添加同步参数。

`oscquery-passive.json`记录25次只读采样，总计3,472ms。在用户原有发送器正常工作时观察到25个不同快照、14个不同Ctl；8个池的完成计数分别增加9/4/9/5/6/8/4/7，共52次worker操作，7个采样看到Busy、1个看到Ready。这证明读取的是变化中的实际运行状态，既非固定默认值，也不是外部测试程序伪造的应答。

可复用的`tools/probe_oscquery_readonly.ps1`通过VRChat进程发现端口，只执行HTTP GET，不绑定或发送UDP、不广播服务、不改配置。它另经4次短采样确认能自动发现并读取；空闲时计数保持不变是正常现象。

官方依据：

- https://docs.vrchat.com/docs/oscquery ：发现/查询与多个OSC应用连接。
- https://docs.vrchat.com/docs/osc-avatar-parameters ：Avatar参数收发、变化输出、Avatar切换。
- https://creators.vrchat.com/avatars/state-behaviors/#avatar-parameter-driver ：本地参数驱动行为。

## ACK能确认到哪一层

| 读回值 | 可说明的事实 | 不足以说明的事实 |
|---|---|---|
| MF6_Ctl / D字节 | 本机参数当前值 | 解码、出生操作已经完成 |
| MF6_LastRx、Q快照、Stage | 接收器锁存/解码阶段 | 所有worker完成或画面正确 |
| 各池DoneCount、Busy、Ready、LastRx | 结合正确的发送基线与预期池，可构造本机执行确认 | 粒子真实数量、GPU像素、其他玩家收到 |

源码依据：`Assets/MorphForge/Editor/Mf6NativeBuild.cs`在Done状态清Busy并递增DoneCount；LastRx在Capture时更新，早于完成，不能单独当作执行ACK。已有本地参数未加入同步MA表达式列表；当前观察到的完成计数已超过4096，也没有按网络Float范围量化。

建议第一阶段先利用现有诊断参数：确认所有相关池空闲，记录完成计数，发送一帧，验证锁存字节和预期序号，再等待本帧涉及的所有池完成计数前进且Busy/Ready均释放。只允许一个未完成帧，异常或头像切换立即放弃旧基线。后续头像增加在Done时复制的AckSeq/AckGeneration，避免用接收序号推断完成。

当前只证明实时回读和生命周期计数可用。没有接入产品发送器、抢占现有通道或测量发送到执行ACK的RTT；HTTP采样间隔不能当作执行时延。当前多字段查询也不能假定具备事务快照语义，实施时需要前后读标记或专门的稳定完成记录。

本机ACK适合背压、判断本机处理落后和排查丢命令。它不能证明远端玩家ACK，也不能据此缩短已验收的250ms多人同步间隔；补播仍要保留。GPU/粒子状态检查仍需要原生测试与图像证据。

自动识别协议和贴图库可沿同一路径增加不同步的常量参数，带版本、能力位、贴图库内容哈希及Ready标记。当前参数名可以识别MF6家族，尚不能精确证明任意自定义贴图库的内容；生产版需在构建时生成对应标记，不能只按前缀猜测。

## 连续区域：先给范围，再传颜色

可以设计为独立的新协议能力，继续使用240bit。MF6现有16种格式均有定义，不能悄悄复用旧格式含义。无需让模型自己打包，外部发布计划器选择编码。

区域描述包括原点、尺寸、扫描轴顺序、材质表与replace/overlay语义。每个数据包携带区域及代次标记、绝对起始索引和数量，从索引计算坐标，不再逐格携带XYZ。索引按最快轴a、其次b、最后c解释：`a=i%Na; b=(i/Na)%Nb; c=i/(Na*Nb)`，再应用轴排列和区域原点。

独立绝对索引是必要条件：若只保存“上包游标+本包数量”，丢一包会把后续所有颜色画到错误位置。区域描述与材质表也是依赖，需要分代、重复发送和完整补播；未收到对应代次的包必须丢弃/等待，不能套用旧表。区域限制最多65,536扫描格，数据包不得越界；实际显示仍受当前对象容量限制，不因节省坐标就变成无限容量。

本次模拟采用保守的固定预算：控制8bit；区域及代次tag16bit、绝对起始索引16bit、数量8bit，共40bit包头；剩余192bit数据。区域描述1帧；通用材质表每条mode3bit+payload24bit，上传包另有32bit头，每帧最多7条。

| 数据形式 | 一帧数据量 | 适用内容 |
|---|---:|---|
| 精确RGB24 | 8格 | 多种独立颜色、渐变与照片像素 |
| 16项材质表，4bit索引 | 48格 | 多色但材质/颜色集合有限的平面或体 |
| 256项材质表，8bit索引 | 24格 | 较大色板，需计入上传色板成本 |
| 2项材质表，1bit索引 | 192格 | 棋盘、双色图案 |
| 数量8bit+4bit索引 | 16段，每段1..256格 | 同材质连续段；每包绝对定位 |

材质表可保存已有贴图引用、RGB或协议已支持的表面编码。这不传输新贴图图片，也不将各类材质精度提高到超出现有载荷范围。

## 与真实MF6规划器的离线对比

运行`cargo run -p morphforge-app --example region_stream_research -- docs/region-ack-research/region-budgets.json`。每个夹具4,096格，先调用产品的实际几何合并，再用实际MF6 Session规划、编码、提交到收敛；不是按单格成本粗算MF6。候选区域方案是未实现的线格式预算，包含首次描述和材质表。RLE比较六种扫描轴序，段长最大256。所有方案统一不计初始Clear、重传与维护补播。

| 夹具 | MF6实际规划帧数 | 区域索引流 | 区域RLE | 区域RGB流 |
|---|---:|---:|---:|---:|
| 单色平面，合并为1 Box | 1 | 24 | 3 | 513 |
| 16色条带，合并为16 Box | 6 | 90 | 5 | 513 |
| 双色棋盘，4,096 Box | 512 | 24 | 195 | 513 |
| 16色随机平面，3,651 Box | 518 | 90 | 245 | 513 |
| 每格独立RGB，4,096 Box | 1,366 | 不用小表 | 不用小表 | 513 |
| 16色分层体，合并为16 Box | 6 | 90 | 5 | 513 |
| 16色随机体，3,516 Box | 516 | 90 | 243 | 513 |

按250ms节拍，仅线传输预算：16色随机平面129.5秒→22.5秒；独立RGB341.5秒→128.25秒；棋盘128秒→6秒。以上不是新头像的实测完成时间。色板上传在小作品上可能得不偿失；同色大平面、大实体应继续用Box，不应强制展开成单格。RLE对随机颜色明显不如直接索引，对连续条带有优势。

## 显示端才是下一处约束

当前MF6每个池一次执行只接收一个出生/删除任务；共有8个池。数据包里装48格，不等于现有头像一轮能产生48个不同颜色的粒子。若保持逐格展开，4,096格仍至少需要512个八池工作轮次，且每轮包括锁存、稳定、擦除、释放和出生。只改Rust压包，可能只省网络而不缩短实际展示时间。

建议两个原生原型按顺序验证：

1. **确定性区域展开器**：局部参数保存一包索引/颜色，从绝对游标生成坐标，分多轮驱动现有8池。测实际解码状态数、CPU、出生速率、背压、丢描述/丢数据后的恢复。先建立正确性与ACK，再评估是否确有吞吐收益。
2. **小块载体**：在新Shader路径中，让一个粒子承载2×2等固定小块。现有浮点24bit保存方式已用于三角面；三段24bit加ColorRGB24在数据预算上可保存4个精确RGB，原生粒子位置用于小块原点，载体Mesh为4个带固定角标的立方体。需要重新验证出生编码、擦除粒度、透明面、Bounds、容量和绘制性能，不能视为已实现。更大的索引小块还需要可持久访问的分区色板，不能假设Shader能读取其他粒子或随意写纹理。

“不传坐标”也不等于能原地改变已出生粒子的颜色。当前颜色和元数据在出生时保存，换色仍需对应重生/替换；要免重生修改必须另外设计Shader可读取的共享色板，且明确它会影响哪些对象。

最终选择器应同时比较当前Box、直接区域RGB、区域索引、区域RLE，并计入描述/色板、局部重绘、接收端处理、重传与补播成本，选择预计实际完成时间最短的候选方案。以上原型和选择器属于后续实现范围，本轮未生成或上传新头像。
