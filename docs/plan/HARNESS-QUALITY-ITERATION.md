# Harness 建模质量追平与超越计划

日期：2026-10-19。审查基线：MorphForge `8a5da10`（0.5.0-rc.1）。状态：**方案设计，尚未实施以下新工具和拦截策略；本轮没有发起付费模型请求。**

目标不是增加 Box 数量或单纯放大上下文，而是在相同任务、参考图、模型、预算下，逐步缩小与用户直接使用 DeepSeek Harness（dsh）的美术差距，再以专用观察和编辑工具争取超过基线。美术结果必须通过配对评测证明，不能由流程测试或模型自评代替。

## 1. 已确认的问题与待验证假设

| 问题 | 证据与当前状态 | 对质量或成本的影响 |
|---|---|---|
| 曾改写请求前缀 | 0.4.2 已修复每轮动态 system、临时参考图和历史图片替换；旧版负对照已复现 | 重复输入失去缓存复用，真实生成成本高；不能把修复前花费当作新版本质量/成本基线 |
| 常驻诊断缺少拦截 | `provider/prefix.rs` 比较出站消息，但 `provider.rs` 只记日志；没有因意外改写暂停 | 看见问题时已可能发出多轮昂贵请求 |
| 重置判定过宽 | 当前 `prefix_configuration_changed` 自动标记 `expectedReset=true`，没有要求对应显式配置操作 | 意外 system/schema 改写也可能被当成合理配置变化；尚未发现0.5.0实际再次发生此类改写 |
| 只显示累计缓存比例 | `provider/usage.rs` 已保存总计/按run用量；`web/usage-ui.js` 的 Prefix 标签使用全局累计率 | 历史正常命中会掩盖当前异常；新会话冷启动也会拉低累计值 |
| 固定截图取景 | `capture_views` 仅有 hero/front/top/side/detail；`web/renderer.js` 的 detail 仍按全场景 bounds 取景 | 看不清脸、窗框、连接和背面；提高整张分辨率未必解决主体太小 |
| 没有严格正交观察 | 当前全为透视相机，front/side略有俯角 | 比例、对称、厚度与遮挡难以准确核对 |
| 可调用造型助手有限 | Recipe SDK有box、line、stairs、wall、roof、frame、镜像、平移、文字；没有专用曲面、扫掠与局部替换接口 | 复杂形体需要模型反复手写算法，更容易退化成阶梯堆盒；不是box表达能力不足 |
| 创作源码不能持续编辑 | 每次Recipe是独立JS执行，函数和变量不保留；日志留了代码，但没有项目级源码模块工具 | 复杂参数化对象难以迭代，重复代码增加输入、错误和修改成本 |
| 局部检查能力弱 | `inspect_region` 只有摘要和前20个Box样本 | 不能可靠回答某个表面、截面、分组结构或覆盖关系；全量返回也不合适 |
| 精细度描述较抽象 | 精细预设要求轮廓/细节/复核，但没有目标格数、特征厚度与视角覆盖契约 | 同一“精细”要求可能被解释成大形加装饰，而没有改善关键轮廓 |
| 历史评测任务主动收紧 | 旧鲸鱼娘要求400 Box以内；部分建筑用例最多两轮截图，并要求尽快保存 | 这些作品不能作为当前1M/384K配置或模型完整建模能力的上限证据 |
| Goal更关注程序条件 | 不同几何hash截图轮数加模型自评，不能识别“改一块凑轮数”或美术退化 | 流程通过不等于比例、识别点、多视角质量通过 |
| 评测未隔离变量 | 旧实验同时改推理强度、提示词、预算或能力，且多为单样本 | 无法确定是哪项改进有效，也不能宣称稳定超过dsh |

待核验：用户实际dsh版本/profile、原始提示词、模型实际路由、thinking/effort、采样参数、图片处理、工具集、运行预算和原始作品。如果其中存在不同，先记录，不直接归因于MorphForge工具。Chat/Responses参数转换、推理内容续传、tool消息配对与看图路径也要做协议对照，确认UI选择真正落到上游请求。

本机已有官方dsh源码快照 `687f282e`。其sdk-minimal说明有持久shell、read_image、工作目录和完整会话记录，工具呈现支持native/PTC。这些是可借鉴机制，不代表用户实际使用该profile，也不证明换成同名工具就能提升模型表现。只读核查官方接口文档不产生建模调用费。

## 2. 先建立常驻费用与缓存监测

检查放在Provider公共出口，覆盖所有创作、续作、重试和compact；不依赖模型自行遵守提示词，不另开付费“监控Agent”。监测读取现有事件与usage，不为检测命中额外发送推理请求。

### 2.1 发送前：客户端前缀一致性

- 在协议转换、图片解析之后检查实际出站payload。固定system/developer、schema顺序、模型、影响模板的选项及已发送历史；记录首个变动的消息/字段与新旧hash，不重复储存整份base64。
- 同一conversation/provider/model/context epoch建立独立基线；compact摘要请求、不同会话和并行工作不能共用错误的比较基线。重启从可用的最后发送记录恢复；没有可靠记录则标记重新建立基线，不能假装已检查。
- 只有配置变更事件、明确reset、成功compact等可解释操作才获得一次预期重置许可；**不得仅因检测到配置变动便自动豁免**。上传引用到期等也须有具体事件及可见提示。
- 未获许可的system/schema或已发送历史改写，默认在发送前暂停当前run、保留场景与待发送请求摘要，停止自动续作。不静默compact、重试、清空上下文或降级为纯文本。
- 区分prepared、发送尝试、完成/失败；不要把没有真正发送的候选payload当成服务端已缓存基线。同样的重试payload不因重复发送被判异常。
- 暂停恢复前重新校验；人工放行是有范围的一次性决定，不永久关闭保护。记录异常和恢复原因，保持打断/插话/队列语义。

### 2.2 响应后：实际缓存命中

保留四个独立指标：结构前缀状态、当前请求缓存率、最近5次有效请求的加权率、当前run/epoch累计率；全局累计移到详情。缓存率只用上游真实usage：DeepSeek hit/miss字段，或兼容接口的cached_tokens。缺失就是未知，不是0%；不能用本地前缀检查代替真实命中。

以下为首版可配置阈值，后续用少量实测校准，不把它们当作服务商保证：

| 状态 | 默认处理 |
|---|---|
| 新连接/新epoch的前两次有效生成请求 | 冷启动观察；仍受总预算限制，结构检查一直有效 |
| 暖机后，稳定前缀且输入至少16k，连续3次有效报告cached=0 | 自动暂停后续请求并说明：结构正常，但上游未复用缓存；不能自动归罪于客户端 |
| 同样条件下，最近5次加权率低于10% | 告警；评测严格模式暂停。新内容占比过大时单列说明，不能要求每轮固定达到90% |
| 上游声明支持usage，但连续2次未提供缓存字段 | 显示未知与覆盖率；评测严格模式暂停，一般创作按明确设置处理 |
| compact/显式配置改变 | 展示重置原因并重新暖机；不无限豁免，也不因此清掉累计账目 |
| 用户显式指定上游不支持缓存/不上报 | 缓存率标未知，结构检查与费用限制继续执行；启动前展示此模式 |

大输入需要更早止损：输入达到128k，或预计一次未缓存输入费用超过配置的风险额度时，首次异常零命中/缺缓存数据即暂停，不等待三次。暖机观察不是免费额度，也不允许为“暖机”额外重发百万Token；所有冷启动和异常开销都进入同一预算。阈值只作用于符合条件的同一会话/epoch样本，不能用其他会话的命中解除告警。

官方缓存是服务端能力；路由、淘汰、并发和模板等都可能影响结果。持续零命中暂停的目的在于止损，不是宣称prefix一定又被客户端改坏。当前请求的费用已经发生，无法靠事后暂停追回。

### 2.3 费用限制与可追溯记录

- 1M/384K仍是能力上限，不能当作每次都应耗满。启动前展示本次Token/时间上限及模型有效限制；金额上限只在价格已配置且来源/日期明确时启用，不硬编码过时价格。
- 发起每次请求前按可用预算决定实际输出上限；输入、可能的未缓存费用和输出保守预留不足时暂停。真实usage到来后结算；缺失、取消和部分响应保留可能已收费的未知项。
- 每次HTTP尝试有attempt ID，关联逻辑request ID。对429/网络失败/截断的重试单独记录，不把多次可能收费的尝试隐藏成一次；不盲目重试中断的长生成。
- 保留输入/输出/reasoning（如报告）、hit/miss、TTFT、耗时、重试、epoch、模型实际ID、工具/提示词/源码版本。可导出按run报告，定位“钱花在重复输入、推理还是工具修复”。
- 新增监测本身不修改模型system和已发送历史；告警显示在应用和本机日志。确需模型调整时只追加新事件说明。

## 2.4 可回放运行时间轴

时间轴是本轮强化的必做项，与P0一起交付：按run、请求、工具批次和revision关联，展示用户输入/插话、上游实际返回的reasoning或reasoning summary、文本输出、工具参数与结果、几何版本、真实截图、compact、暂停/错误、Token和缓存状态。未返回思考内容时明确显示“上游未提供”，不推断或伪造隐藏思考。

支持流式追加、搜索/类型/run筛选、展开代码和错误、图片预览、只读查看历史revision与返回当前编辑状态、历史分页和重启后读取。历史查看不发模型请求，不覆盖工程，不发OSC，不把浏览事件写回模型上下文。原始事件继续保留，界面读取有界的轻量投影，避免每次刷新搬运全部请求/base64。流式思考来自实际事件，标注未完成/已完成，不能将中断的部分工具当作已执行。

每个卡片关联真实事件seq/request ID/tool_call ID，费用未知与缓存未知保持未知。展示/导出对已知密钥脱敏，使用文本节点渲染模型内容。后续可增加按关键帧播放；首版优先保证可靠查询、流式观察和版本回看。

## 3. 工具与创作工作区

保留当前少量原生工具和run_recipe的批量执行优势。先扩充确定性的SDK与工具参数，避免把每个原子造型都变成一次模型网络请求。工具定义在会话内稳定，说明文档按需读取，不每轮重建schema。

SDK说明、工具参数和真实实现从同一份版本化契约导出并验证，避免“实现有、模型不知道”或描述参数实际不支持。曲面助手可接收连续几何参数，在内部按统一规则采样/取整，最终仍输出合法整数网格；不要要求模型为每个曲面点自行拼凑整数取整。

| 方向 | 拟定接口/行为 | 首批验证 |
|---|---|---|
| 自由视角与局部观察 | 扩展capture_views：旧views兼容，新增shots；支持组/包围盒自动fit、yaw/pitch、透视/正交、margin、背景和分辨率；必要时精确position/target | 已知非对称模型六方向、局部占画面比例、坐标一致、无裁切、透视/正交回执 |
| 相机书签与图片重读 | 保存可复现camera配置；read_artifact重新看已有图片或裁剪参考图，不为重看重渲染；标注来源、revision、裁剪范围 | artifact不存在/版本陈旧明确报错；裁剪不是新几何证据 |
| 场景和截面检查 | 扩展inspect_region/scene：分组bounds/材质/数量、分页稳定样本、指定轴切片、有限体素查询、revision差异 | 不展开整个256³空间，读操作有边界，统计与实际几何一致 |
| 曲面与连续轮廓 | SDK提供ellipsoid、cylinder、cone/frustum、capsule、tube/polyline、polygon extrusion、旋转截面等，仍生成普通体素 | 几何oracle、边界/整数取整、空心厚度、连续性、资源上限、固定seed重现 |
| 安全局部修改 | 显式replace_group/remove_group、组变换与有作用域的切削/换色；先dry-run返回影响与分裂/合并数量 | 不误删邻组、保护仍生效、baseRevision/幂等/撤销正确 |
| 可持续编辑源码 | 项目内虚拟文件工具read/patch/run，保存main recipe、参数和可复用模块；每次仍用新JS沙箱加载选定文件版本 | 源码hash和几何revision关联；补丁失败原子回滚，重启/compact后可继续 |
| 色板与表面层次 | 复用define_palette，增加可控的区域配色/确定性纹理助手；材质表现与造型分开检查 | 不用随机噪点掩盖差轮廓；本机艺术与VRC可导出能力分别报告 |

建议的截图参数示意（新接口提案，当前不可调用）：

```json
{
  "revision": 17,
  "shots": [
    {"id":"front-check","fit":{"group":"character"},"projection":"orthographic","yaw":0,"pitch":0,"margin":0.1},
    {"id":"face-detail","fit":{"group":"face"},"projection":"perspective","yaw":20,"pitch":5,"margin":0.15}
  ],
  "width": 1024,
  "height": 1024
}
```

坐标保持+Z为正面、Y向上；yaw=0从+Z看向目标。回执返回实际camera、fit bounds、revision、几何/材质hash和artifact。诊断视图明确区分正常作品视图：隔离组、隐藏遮挡物不能用来声称整件作品中可见。最终仍须检查完整场景。

虚拟工作区只允许工程目录内的创作代码与数据，不为追求dsh形式直接开放整个Windows文件系统或任意shell。全局变量无需跨进程长驻：**持久化可编辑的程序和参数比维持不可追踪的JS内存更重要**。源码、Recipe展开结果与截图均能回放，compact只摘要对话，不丢失造型程序。

## 4. 从“堆Box”改为可观察的精度契约

不全局禁止大Box，也不要求固定最低Box数：同一体素形状合并后Box数可大幅下降，平墙/底座适合大Box。全局强制1³会增加成本而不改变几何。

精度按主体尺度、曲率和识别点定义：

1. 首轮明确主题、正面、主体尺寸、3～6个关键识别点以及优先检查的视角。精雕档可试用主体最长边128～192格作为起点；具体依任务、资源和是否VRC决定，不硬套所有作品。
2. 大形用大Box；曲面、斜边和剪影要求逐层截面或连续路径。关键眼睛、窗框、边缘等使用1～2格可辨结构；在目标截图中仍看不清则局部放大检查。
3. 分阶段验收比例/轮廓→次级形体与负空间→识别细节→配色/表面层次。不能用新增随机装饰代替修正头身比、屋顶形状、尾鳍或门窗遮挡。
4. 每轮只选明确的可见缺陷，给出下一步局部修改目标与预期观察视角；记录修改前后截图。不强制每次看图必须改几何，也不允许改一格充复核轮数。
5. 截图覆盖与关键识别点记录替代单一“达到三轮即可完成”。hard gate只检查可证明的版本、视角和保存条件，美术判断仍靠独立审阅。
6. 保留候选版本，若新修改退化可恢复较好版本。最终报告真实短板，不以goal=achieved证明美术无缺陷。

提示词拆为短而固定的运行规则、稳定工具契约、三档创作策略和本次任务要求。创作策略区分草图/标准/精雕；安全、版本与保护规则不随实验删除。无实际证据前不因“dsh适配”随意改工具名称或全面切换PTC；以独立消融决定哪种呈现更有效。

## 5. 建立公平的dsh对照

两条对照分开报告：

- **用户实际dsh工作流**：保留其原始工具、提示词、输出与预算，导入可比较的体素结果，作为体验目标。若原作品是任意mesh或使用额外人工修改，单列差异，不能直接用像素分数证明体素Harness更差。
- **同工具受控对照**：为dsh提供MorphForge CLI/MCP薄适配，调用相同Rust几何、相机、图片和作品库；同模型/上游/effort/采样参数、参考图、预算和初始场景。这样可区分“agent循环与提示词”问题和“造型工具”问题。

先复用已有dsh轨迹和作品，不为凑基线再次付费。没有原始轨迹时明确标为不可完整复现。固定截图光照、材质、相机、分辨率及缩放；同时看全局和关键局部，不能各挑有利角度。

首批任务建议：曲面角色（鲸鱼娘）、负空间结构（椅子/拱桥）、多层建筑（灯塔/云港）、体素中文标牌。先挑其中两个做低预算试验，缺陷定位清楚后再扩展至5题×3次；重复次数和总费用事前固定，未通过监测不进入这一步。

| 评估 | 方法 |
|---|---|
| 美术主指标 | 隐去系统名称的配对审阅：轮廓与比例35%、关键识别点25%、配色与层次20%、多视角一致性10%、可编辑交付10%；原始偏好票同时保留 |
| 工程门槛 | 实际可加载、保存、继续编辑；无越过保护、无虚报截图；若目标VRC再检查导出兼容 |
| 成本 | 实际input/output/cached、未知usage、尝试次数、时间、人工续作次数；官方价格已配置时另算金额 |
| 稳定性 | 成功/失败/预算耗尽全部计入，不只展示最好一张；报告样本量和不确定性 |
| 表达效率 | 对象尺度、占用体素、表面特征、合并后的Box数；Box数不是艺术得分 |

人工盲评优先，像素/轮廓指标只做辅助。额外模型评审不是默认项目，不能未计费便加入循环。库复用与从零创作分赛道，避免内置示例泄露答案；不只在调提示词的同题上验收，另留未见任务。相同seed只能固定Recipe随机性，不能保证不同上游的生成逐字一致。

“接近”的候选门槛：在同预算配对中至少80%任务不劣于dsh（包含平局）且无工程退化；“超过”需出现稳定偏好和相同质量下更低成本/耗时。以上是验收目标，不是当前已实现结论；小样本只用于方向筛选，不声称统计显著。

## 6. 执行顺序与费用闸门

| 阶段 | 交付 | 进入下一阶段的条件 | 模型费用 |
|---|---|---|---|
| P0 止损与基线 | 常驻前缀/usage监测、自动暂停、严格评测预算、可回放时间轴；归档已有dsh输入和作品 | 模拟重写在发送前被拒绝；零命中/缺usage/compact/重试的离线用例通过，监测不破坏append-only | 无新增生成费用 |
| P1 视觉闭环 | 自由/局部/正交截图、相机书签、图片重读、局部几何查询 | 已知非对称几何与图片回执一致、可复现、没有裁切和版本混淆 | 无需付费模型，可协议fixture测试 |
| P2 可持续造型 | 源码工作区、组级修改、首批曲面/扫掠助手 | 固定源码稳定重现，错误/撤销/保护测试通过；高精度手写参考Recipe成功 | 无需付费模型 |
| P3 最小对照 | 一个曲面题和一个负空间题，旧策略/新策略，尽量复用旧轨迹 | 每次生成前检查预算，暖机后常驻检查命中；逐项审阅提升与退化，先不全量跑 | 明确小额封顶；异常立即暂停 |
| P4 单变量迭代 | 依次比较相机、几何助手、源码复用、精度提示词、Goal策略及工具呈现 | 每轮只改一组变量；能解释收益再保留，不盲目累加要求 | 共用整轮封顶，未用完不自动续费 |
| P5 保留集与交付 | 多题多次对照、Windows验证、文档和候选安装包 | 质量/成本/稳定性报告可审阅；达到门槛才宣称接近或超过 | 另有明确总预算，不因1M窗口自动放开 |

P0必须先于任何新的大额真模型评测。日常创作同样启用常驻监测，评测严格模式只在缺usage/低命中策略上更保守。用户内网本机可运行透明代理辅助诊断；此处不能直连内网，不假装已经验证其真实KV-cache。

用户已授权在常驻监测有效的情况下开始强化迭代和受限真实模型测试。先完成P0/P1与离线验证，再做P2和小额对照；真实缓存未报告或异常时停止继续付费，不将结构前缀通过冒充真实缓存命中。实施记录与原设计状态分别保存。
