# 母粒子出生时序回归

2026-10-19。在16k UDP长测、Windows并行编译期间，出现两类差额：接收命令少于发送命令，以及执行完成后实际方块少于已接收绘制数。不能把这轮称为无损通过。

独立复制原生 Store/Pump 夹具，保持产品显示池不变，以 `ParticleSystem.Simulate` 注入帧跨度：

| 母粒子寿命 | 16ms帧 | 33ms帧 | 100ms帧 | 300ms帧 |
|---|---:|---:|---:|---:|
|25ms|1|1|0|0|
|100ms|1|1|1|1|
|500ms|1|1|1|1|

数字为一次激活实际出生的 Store 子粒子数量。25ms母粒子可在长帧内死亡并漏掉Birth子发射，参数命令计数仍可能正常。

连续8次、每次250ms激活测试：25ms寿命得到7个子粒子；100ms和500ms得到8个。选500ms增加长帧余量；母粒子对象仍由Flow在下一阶段停用，寿命不是提交等待时间。目标方块粒子仍为无限寿命。

在 `2026-10-18T19:53:34.768Z`（北京时间10月19日03:53:34）对正在运行的Play实例应用500ms寿命，并记录 `Docs/Stage4/pump-runtime-patch.json`。保守地以绘制索引3840以后作为修复后区段。后续测试将分别统计该区段和此前缺失，并在全量传输结束后检查补发/容量/删除回收。最终资产由 `Mf3DisplayBuild` 固化同一设置。

该修改解决已复现的发射时序问题，不提供网络ACK，也不能恢复Editor阻塞时未被动画器捕获的OSC参数。最终报告必须分别列发送、接收、完成和实际唯一方块数量。

原始报告保存为 `capacity-first-pass.json`，Windows 原生粒子快照另存 `Docs/Stage4/capacity-first-pass-particles.bin`，报告记录 SHA-256。后续补发不覆盖该首遍证据。此轮证明低帧或并行负载下不能把 0.25s 无 ACK 的参数输入当作可靠队列，也没有证明最终 Fire 30ms 版本的完整首遍成功率。

正式资产还将 Fire 窗口从 1ms 延长到 30ms，并另做协议与连续发送回归。长帧仍可导致参数采样丢失，因此产品继续按无远端 ACK 设计，保留周期全量刷新和可调发送间隔，不能承诺任意负载下零丢失。
